# SpektraFilm iOS 16.5.1 — v1.8.24 Build 49

## Larger ORIGINAL nonlinear photos, without lowering algorithm precision

The user has verified that their 3888×2592 (10,077,696px) photo exports
in the original 8-bit source DIR mode on real iPhone. v1.8.22 and v1.8.23
*full nonlinear per-pixel film→paper optical mode* was artificially capped
at 2MP solely to limit peak memory, NOT because the hardware could only
export 2MP.

This revision migrates THREE related parts together:

1. **Exact source FIR/YVV memory architecture.** The new
   `SourceSpatialDIRConvolution.diffuseMemoryBounded` applies the original
   Gaussian FIR's vertical→horizontal reflect passes and the original YVV
   horizontal→vertical 3rd-order forward/backward recurrences over the
   **ENTIRE source image**. The exact same core+three exponential-mixture
   weighted contributions are accumulated in the same per-pixel arithmetic
   order. Instead of allocating four large 3-channel filtered full frames,
   it reuses TWO 1-channel Double workspaces for all components and channels.
   No stripes, truncated halo, independent-tile boundary resets, Float32
   buffer conversion or approximate Gaussian filter is used.
2. **In-place source nonlinear optical stages.** The app's actual
   `OriginalSourcePhysicalImage.developInPlace` uses the *single existing*
   ImageIO Double RGB input buffer sequentially for encoded input, the
   upstream Hanatos log-exposure, and final original physical paper/ACES
   scanner RGB output. It retains only a source 3-channel inhibitor image
   and 3-channel diffused image (the former released after filtering).
   Original measured film H-D, source DIR matrix, pre-DIR H-D, 81-wavelength
   physical negative printing and s023 paper H-D remain executed per pixel
   at real original dimensions. This is a memory ownership change, NOT
   changing the physical formulas or their parameter order. The non-inplace
   public diagnostic `develop()` continues to call the identical production
   in-place engine and preserve stage-level observers.
3. **Conditional full-resolution admission / truthful UI.** The previous
   hard 2,000,000-pixel cap is replaced by an **experimental 12,000,000-
   pixel ceiling** and a separate measured-device memory preflight
   **before ImageIO allocates a full CGImage**. It estimates 120 B/pixel,
   checks min(1.5GB, physicalRAM/3), and requires an extra 20% process
   headroom margin using `os_proc_available_memory` on iOS 16.5.1.
   `SafeExportResolution` now displays the 120 B/pixel estimate in the
   confirmation sheet for the physical mode, rather than wrongly showing
   generic 104 B/pixel. The original 16MP direct ImageIO/Double DIR export
   and mobile safe/economy export algorithms remain unchanged.
   The Photo Library saver and both original preview/export paths remain.

## Independent numerical regressions

- 24 varied FIR/YVV combinations (sizes including 23×17, 31×7,
  2×1 and 1×13, Gaussian sigmas straddling 0.5/3 and tail mixtures).
  The reused-channel Double implementation is compared pointwise
  against the ORIGINAL, previously Python-verified full-allocation
  Swift implementation; any channel delta >5e-13 is an error.
- Three independent Python original source whole-image nonlinear camera,
  film H-D, physical DIR, paper s023 and ACES scan fixtures remain gated,
  seven Double stage vectors each, with actual UIImage pixel decoding.
- Source original Python 3× multi-size FIR/YVV full-frame DIR regression
  (871,422 RGB channels, eight stages), film/paper/scanner/Poisson/MT and
  iPhoneOS Build49 validation remain mandatory and unchanged.
- Simulated iPhone memory profile for user's 3888×2592 input:
  physical RAM 4.5GB and available process 3.14GB => *can attempt*
  original-size optics. With smaller process memory or physical RAM the
  **same size must be rejected** with explicit budget and no fallbacks.
  Inputs >12MP must still be refused. An extrapolated budget is not
  a hardware measurement; peak memory/jetsam may differ on real iPhone.

## Important remaining limits

**Not yet certified on real iPhone:** 10.08MP original physical export
successful completion, actual memory peak, sustained CPU time, battery/
thermal behavior, Photos save. Real-device testing is required and failure
must be reported as failure, not disguised by lowering resolution.
12MP is an upper compatibility guard, NOT a guarantee.

**Not fully ported:** true source all-Float64 measured profile data
(current stock samples were prepacked Float32), Numba parallel random
stream and grain, full optical halation, RAW/ProRAW, and exact full
original default CAM16/scanner finish. Existing strict
`verify_precision_release.py` remains fail-closed. Only publish an
experimental unsigned `UNVERIFIED-TEST` IPA until original full-image
physical-iPhone numerical parity can actually be shown.

## User regression procedure

On the user's iOS 16.5.1 iPhone:
1. Use the known 3888×2592 tagged opaque sRGB image.
2. Select original source Hanatos Float64, source FIR/YVV DIR, original
   physical negative enlarger and original ACES scanner.
3. Enable 8-bit original source pixel input and the explicit opt-in
   `逐像素全光学（实验）`; disable grain, halation and unsupported options.
4. Choose **original full resolution**, verify the export confirmation
   now states 3888×2592 and about 1209MB estimated peak. Start export.
5. Verify JPEG dimensions, visual output and Photos save; report crash,
   jetsam, black image, peak memory or slowness separately. If memory
   preflight refuses it, report the real budget/headroom numbers.
6. Turn OFF full optical experiment to confirm original 10MP
   v1.8.23 source-DIR export still works exactly as before.
